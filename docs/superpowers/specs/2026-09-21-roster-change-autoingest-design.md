# Roster Change Auto-Ingest — Design Spec

**Date:** 2026-09-21
**Status:** ON HOLD — design captured, explicit decision to implement later
**Security decision (email gate):** PENDING — not resolved. See "Open items" §.
**Repo:** `marcryan/lanyard` (branch `main`, GitHub Pages site)

## Problem

When a user submits a roster change in the app, the app emails a structured "Roster Update"
message. We want that email to flow into the Hermes gateway and automatically update the
corresponding roster JSON on GitHub, so the live site reflects the change without manual editing.

## Goals

1. A submitted roster change from the app updates the correct roster file on `origin/main`
   and the live site serves the new data.
2. Routine changes apply automatically (add / update / move) with a push.
3. A true conflict never corrupts roster data and never auto-pushes — it notifies the owner.
4. Deterministic, no-LLM data mutation; the agent orchestrates, a script guarantees correctness.

## Non-goals

- No agent-driven (LLM) editing of roster JSON directly before push.
- No changes to the CIAC export files (`roster_<sport>.json`) — they remain faithful scrape mirrors.
- No second IMAP consumer racing the gateway for the same mailbox.
- No changes to the "Request a feature" email flow.

## Environment facts (verified)

- Email platform is wired into the gateway: `erasmus.helps@gmail.com`, IMAP poll every 15s.
  - `EMAIL_IMAP_HOST=imap.gmail.com`, `EMAIL_IMAP_PORT=993`
  - `EMAIL_ALLOWED_USERS=marc@darkmatter.com` (From-based allowlist, currently)
  - `EMAIL_HOME_ADDRESS=marc@darkmatter.com` (cron/notification delivery target)
- The gateway's inbound gate keys on **`From:` only** (`plugins/platforms/email/adapter.py::_sender_accepted`).
  It drops any sender not in `EMAIL_ALLOWED_USERS` (or unmatched under allow-all) before dispatch.
- The aliasing system (SimpleLogin) rewrites `From:` per sender (e.g.
  `marc_ryan_at_abcsinsights_com_nujaza@simplelogin.co`), so `From:` is **not** stable.
- The stable invariant on every forwarded roster email is the **`To:` recipient =
  `rosterupdate@aleburd.com`** (verified via a live test email: From alias, To rosterupdate@aleburd.com).

## Design

### 0. App change (PENDING — reverted, re-apply at implementation)

  (was `lanyard@aleburd.com`). "Request a feature" is unchanged and still goes to
  `lanyard@aleburd.com`. **NOTE: this edit is currently REVERTED / unapplied — it was made during
  the session then reverted when the work was put on hold. It must be re-applied as part of
  implementation.** This routes roster changes through the owner's SimpleLogin alias into the
  gateway inbox.
- Pending commit along with this change set.

### 1. Trigger

A forwarded roster email lands in `erasmus.helps@gmail.com` → the gateway IMAP poll delivers it
as an inbound run. Processing proceeds only when **both** hold:

- The email's recipient contains `rosterupdate@aleburd.com`, and
- The body parses as a well-formed roster change.

### 2. Config change (PENDING — security decision open)

**Security gate decision is NOT resolved.** The user explicitly rejected `EMAIL_ALLOW_ALL_USERS=true`
(any sender = open-world exposure). Two candidate approaches were tabled:

- **A — Patch the email adapter** (`plugins/platforms/email/adapter.py::_sender_accepted`) to support
  domain-suffix allowlist entries (e.g. `@simplelogin.co` matches any `*@simplelogin.co`) alongside
  exact addresses, preserving deny-by-default. Risk: it modifies a git-checkout install
  (`~/.hermes/hermes-agent`, origin NousResearch/hermes-agent); a `hermes update`/`git pull`
  overwrites it (re-apply or upstream).
- **B — No source change**; dedicated scheduled polling for new `To: rosterupdate@aleburd.com` mail,
  validating recipient + body, keeping the generic allowlist closed. Cost: a second IMAP consumer
  (mailbox race with the gateway).

Decide A or B before implementing. Recommended: A.

### 3. Parse & match

Body is structured (generated by the app):

```
Send this note without editing it.


Roster Change
Roster: <manifest name, e.g. "Football Varsity">
Number: <n>
First Name: <first>
Last Name: <last>
Grade: <Freshman|Sophomore|Junior|Senior>
```

- Parse deterministically into fields. Grade values already match the app's native `year`
  vocabulary — no conversion.
- Resolve the roster: look up the `Roster:` value (a manifest `name`) in `rosters/rosters.json`
  → `id` → target file `rosters/roster-app-<id>.json`. **App-format files only.**
- If the roster name doesn't resolve to a known id, treat as unparseable (see §6).

### 4. Apply

Given `{roster_id, number, first, last, year}` against the target roster-app file:

1. **Number exists on roster** → update that player's `name`/`year` in place.
2. **New number, name not present** → append a new `{number, name, year}` row.
3. **New number, name already present under a different number on the same roster** →
   a **move**: remove the old entry, add under the submitted number.
4. **True conflict** (the submitted number is held by someone else, AND the submitted name
   matches a different existing number — i.e. both the number is claimed and the name is being
   moved) → **do not push**. Email the owner a conflict notice with the detail.
5. Re-sort players by number before writing (app convention).
6. Preserve any dual/duplicate numbers already in the source verbatim; only the targeted change
   is made. Do not dedupe existing rows.

### 5. Push

- Commit with a message like `Roster update: <sport> #<n> <name>`.
- Push to `origin/main`. The site serves from `main`, so the push publishes the change.
- Confirm the result to the owner (subject line: pushed what/where, or the conflict).

### 6. Do not push on

- Unparseable/empty body, or missing required field(s).
- `To:` recipient that does not contain `rosterupdate@aleburd.com`.
- Unknown roster name (no matching id in `rosters.json`).
- True conflict (§4.4).
These are reported to the owner; nothing is written or pushed.

## Mechanics / components

1. **Skill** — a dedicated skill documents the workflow: recognizing the inbound email, running
   the parser, reviewing its output, and confirming. Owns the orchestration & human-facing loop.
2. **No-LLM Python script** — `misc/process_roster_change.py` (gitignored, like other `misc/`
   dev artifacts): given the parsed fields + roster id, it mutates the roster-app JSON, re-sorts,
   commits, and pushes. Pure function over data; no LLM judgment inside.
3. **Config** — `EMAIL_ALLOW_ALL_USERS=true` in the email platform env.
4. **App** — single recipient change, already made (pending commit).

The script operates on the message the gateway already delivered (passing parsed fields +
roster id), so there is no second IMAP consumer and no mailbox race with the gateway.
